# Karpathy Coding Guidelines (LLM 코딩 행동 지침)

> **출처**: Andrej Karpathy의 LLM 코딩 약점 관찰을 정리한 4가지 행동 원칙.
> **로드 시점**: `/harness:execute` 단계의 의무 로드 (코드 작성·수정 시).
> **언어 우선순위**: 보안 정책(`rules/common/security.md` — 7단계 도입 예정) > 본 가이드라인 > 일반 코딩 스타일.

---

## 1. Think Before Coding (가정을 표면화)

> "Don't assume. Don't hide confusion. Surface tradeoffs."

- **가정을 명시한다.** 불확실하면 코드 작성 전에 질문한다.
- **여러 해석이 있으면 침묵하지 않는다.** 후보를 모두 제시하고 사용자가 선택하게 한다.
- **더 간단한 방법이 보이면 제안한다.** 계획에 있더라도 명백히 더 단순한 길이 있으면 짚는다.
- **혼란스러우면 멈춘다.** 추측으로 진행해 후반에 폭증하는 재작업 비용을 회피한다.

**적용 예시 (`/harness:execute` 진입 시):**
```
plan/{N}.md를 읽었으나 다음이 명확하지 않습니다:
- (가정 A) 입력 인코딩은 UTF-8로 가정합니다 — 맞습니까?
- (해석 B vs C) "안전한 저장"이 (B) 디스크 암호화 vs (C) 환경변수만 의미하는지 모호합니다.
이 두 가지를 확정해야 작업을 시작할 수 있습니다.
```

---

## 2. Simplicity First (요청 이상은 작성 금지)

> "Minimum code that solves the problem. Nothing speculative."

- **요청받은 것 이상의 기능 추가 금지.** 미래의 가상 요구사항을 위해 추상화하지 않는다.
- **일회용 코드에 추상화 불필요.** 한 번 쓰고 버릴 코드면 그렇게 작성한다.
- **요청받지 않은 유연성/설정 옵션 제외.** 기본값 한 가지로 시작한다.
- **불가능한 시나리오의 에러 처리 제거.** 시스템 경계(외부 API, 사용자 입력)에만 유효성 검사를 둔다.
- **점검 질문**: "시니어 엔지니어가 이걸 보고 과설계라고 할까?" → Yes면 단순화.

**적용 예시:**
- ❌ "장래 다양한 인증 방식을 지원할 수 있도록 `AuthStrategy` 인터페이스를 추상화"
- ✅ "현재 요구되는 Bearer Token 검증만 구현. 다른 방식이 실제로 필요해지면 그때 리팩터"

---

## 3. Surgical Changes (필요한 것만 수정)

> "Touch only what you must. Clean up only your own mess."

- **인접 코드의 "개선" 금지.** 포맷, 변수명, 구조 변경은 요청받지 않은 한 손대지 않는다.
- **작동하는 코드 리팩토링 금지.** 변경 범위는 `plan/{N}.md`에 명시된 것만.
- **기존 스타일 유지.** 본인이라면 다르게 짤 코드라도 주변과 일관성을 우선한다.
- **본인이 만든 잔재만 정리한다.** 본인 변경으로 미사용이 된 import/변수만 제거.
- **기존 데드코드는 보고만 하고 삭제 금지.** 별도 태스크로 분리.

**적용 예시:**
- ❌ 함수 하나 수정하다가 같은 파일 내 다른 함수의 "더 나은 코드" 발견 → 같이 수정
- ✅ 다른 함수의 개선점 발견 → `history.md`에 "차후 개선 후보" 로 기록만 하고 손대지 않음

---

## 4. Goal-Driven Execution (검증 가능한 성공 기준)

> "Define success criteria. Loop until verified."

- **모호한 목표를 검증 가능한 형태로 변환한다.** "작동하게 하기" → "테스트 X 작성 → 통과 확인".
- **각 단계에 구체적 검증 명령을 명시한다.** (`pytest`, `curl`, 출력 비교 등)
- **부정 케이스도 검증한다.** 잘못된 입력에 의도된 에러 발생을 확인한다.
- **검증 통과까지 자율 루프 가능.** 강한 성공 기준이 있으면 사용자 개입 없이 반복 시도해도 안전.

**적용 예시 (`plan/{N}.md` 검증 기준 포맷):**
```markdown
## 성공 기준 (Verification)
- [ ] 검증 명령: `pytest tests/test_auth.py::test_jwt_invalid -v`
- [ ] 통과 조건: exit code 0, 출력에 `1 passed` 포함
- [ ] 부정 케이스: 만료 토큰 입력 시 `401 Unauthorized` 반환 확인
- [ ] 회귀 검증: 기존 `tests/test_auth.py` 전체 pass 유지
```

## 트레이드오프 (사용자 결정 사항)

본 가이드라인은 **속도보다 신중함을 선호**한다. 다음의 경우 판단으로 완화 가능:
- 일회성 스크립트, 프로토타입, 학습용 코드 — 단순화 가능
- 마감 임박한 핫픽스 — "Surgical" 더 엄격, "Simplicity" 더 엄격
- 명백한 자명한 변경 — "Think Before" 생략 가능

**의심스러우면 사용자에게 확인.** 침묵으로 가정하지 않는다 (= 1번 원칙).

---

## 보안 엔지니어 페르소나 적용 우선순위

`/harness:execute` 단계에서 충돌 발생 시:
1. `rules/common/security.md` (보안 정책 — 7단계 후 도입)
2. **이 문서 (Karpathy 4원칙)**
3. `plan/{N}.md` 의 구체 지시
4. 일반 코딩 스타일

상위 항목이 하위 항목과 충돌하면 상위가 우선한다. 단, **충돌 자체를 사용자에게 알린다** (1번 원칙).
